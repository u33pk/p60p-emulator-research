# 77. 定性：画面是冻结帧 + 输入全链路断（2026-10-22）

## 起因

用户提出假设：guest 截图黑屏、host 截图是桌面、滑动无效——是否其实是「虚拟机渲染出一帧后整体卡死」，而「uinput 注入在 enforcing 下未生效」是误判？本次逐层验证。

## 验证方法与结论

### 1. 虚拟机没有整体卡死（推翻"卡死"说）

- `/proc/stat` CPU jiffies 10 秒内 user+82 / sys+133 / idle+3806，内核在持续调度
- samgr / foundation / sceneboard / composer_host / render_service / multimodalinput 全部存活
- sceneboard（pid 5312）主线程持续处理事件（NetSpeedController、nearlink、状态栏），日志时间戳就在注入操作前后
- `power-shell suspend` 下发后 composer_host 立即响应（16:02:00 `CommitComposeLayer! 10`）

### 2. 但画面确实是一帧冻结帧（证实现象）

- 锁屏时钟停在 `03:19`（= 开机时刻 15:19 的 12 小时制），40 分钟未动
- 多次宿主窗口截图字节级完全相同（cmp IDENTICAL）
- `power-shell suspend`（应黑屏）+ `wakeup` 后画面依然字节级不变
- 宿主 `qemu.log`：`express_display.c(opengl_paint_composer_layers)` 最后一次被调用是 **15:18:22**（开机后约 1 分钟内，伴随两次 `not support transform_type 8` 错误），此后再无任何 paint 请求到达宿主——包括 16:02 guest 侧确实发生的 Commit

**结论：guest 合成器仍在工作，但合成结果没有流过 express_display 通道到宿主窗口。冻结点约在 boot-complete（15:19:20）前后，疑似与 live-present 切换或 transform_type 8 错误后通道状态损坏有关。**

### 3. "uinput 注入在 enforcing 下未生效"是错误归因（证实用户质疑）

输入实际是**整条链路断**，与 enforcing 无关：

- 宿主 XTEST 真实鼠标拖拽 + 按键注入（与真实输入不可区分）→ guest 全部 9 个 `/dev/input/event*` 节点 **0 字节**；virtio 鼠标（virtio7）中断计数开机以来恒为 0 → 宿主输入从未进入 guest 内核
- guest 内部 `uinput -T -g` 注入 → samgr 访问 MMI（sa 3101）被 SELinux 拒绝但 `permissive=1` 放行，此后 MMI 零分发日志 → 注入被静默吞掉
- express 多点触控的 guest 端守护 `uinput_inject`（pid 269）是空壳：fd 只有 `/dev/null`，未持有任何设备；`/dev/uinput` 不存在
- 5 个 "virtio touchscreen"（event2-6，/devices/virtual/input）是启动早期创建的虚拟设备，之后无任何数据流过

## 修正后的问题清单

| 问题 | 真实断点 | 备注 |
|---|---|---|
| 画面冻结 | guest composer Commit 之后 → 宿主 express_display paint 之前 | 约 boot-complete 时刻断流，guest 侧无报错 |
| 宿主输入无效 | 宿主 UI → express_pipe → uinput_inject（空壳）→ /dev/uinput（缺失） | 快递多点触控链未建立 |
| guest 内 uinput 无效 | uinput 工具拿到 MMI SA 后被静默吞掉 | 待查 MMI 内部鉴权/处理 |
| guest 截图黑屏 | capture 缓冲与呈现缓冲不一致 | 已知无害，独立问题 |

## 下一步候选
