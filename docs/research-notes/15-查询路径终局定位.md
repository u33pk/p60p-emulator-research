# 15 - 查询路径终局定位：stub 分发表 [obj+0x38] 的处理函数返回 0

日期：2026-10-18（夜二场）
决定性进展：**查询的真实执行路径找到了，且证实它不经过服务表查询函数**。

## 1. 三连信号实验结果

| 陷阱点 | 结果 | 结论 |
|--------|------|------|
| DevSvcManagerGetObject 入口（0xb44c→udf） | **整轮零触发**，devmgr 安然存活 | **所有查询都不走 GetObject**——我反编译+内存取证的 hash 环链 walk 不是活动查询路径（或不是唯一路径） |
| stub 分发表调用 `blr x20`（0x10018→udf，x20=[x19+0x38]） | **devmgr SIGILL 崩溃循环**（21.67s 起，每次查询都死） | 查询确实经由 fcn.febc 的 `ldr x20,[x19,0x38]; blr x20` 分发到一个**处理函数**，该函数对 display_composer（及 battery_extra 等）返回 0 → 0x10020 跳 0x107bc 打 "not found" |

## 2. 机制结论

devmgr 的 stub 对象（x19）在 +0x38 持有**按查询码索引的处理函数**（sbuf code 经 `ror 2` 即除 4 作为索引）。107 客户端发来的 get 查询码经此分发表路由到某个处理函数，**该函数没有查服务表就直接返回 0**。这与 add 路径（走 DevSvcManagerStubAddService 成功）不是同一张表/同一套码值——**48 devmgr 与 107 客户端的 servmgr 协议在查询码或对象类上不匹配**是最终根因方向。

旁证：add 成功日志 4 条（含 composer）；查询 not-found 71 条；两者用不同处理函数。

代价记录：blr 陷阱导致 devmgr 崩溃循环 → critical 4 次 → 24s sysrq panic（预期内，已还原）。

## 3. 下一步（聚焦）

1. **静态识别 [obj+0x38] 表**：反编译 stub 对象构造（DevSvcManagerStubStart @0x11aa0 一带），列出 +0x38 处的函数表内容（哪些处理函数、get 码应落哪一项），与 107 客户端的查询码对照，找出错位。
2. **错位修正**（二选一）：
   a. devmgr 侧：把分发表中 get 码对应的项改为 `DevSvcManagerGetObject` 的适配包装（或直接改索引计算）
   b. 客户端侧：patch 107 libhdi/libhdf_ipc_adapter 的查询码为 48 期望值
3. 修正后验证：snapshot_display 出图 → 桌面 → docs 收尾。
