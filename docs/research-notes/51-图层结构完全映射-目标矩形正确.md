本地副本映射（`buf+4+idx*60` 整块复制到 `x29+0x70`）：

```
x29+0x70 ← layer+0x00    x29+0x90 ← layer+0x20
x29+0x78 ← layer+0x08    x29+0x98 ← layer+0x28

x29+0x88 ← layer+0x18    x29+0xa8 ← layer+0x38(4字节)
```

## 目标矩形计算（实证，`0x795fcc` 起）

```
dest_w = obj_w × layer[0x0c] / layer[0x24]   = 1320 × 1320 / 1320 = 1320
dest_h = obj_h × layer[0x10] / layer[0x28]   = 2232 × 2232 / 2232 = 2232
```

`obj` = `lookup(layer+0x34)` 的返回值，`obj+0x78` = **1320**（已实测，见下）。
目标矩形 **1320×2232，满屏，完全正确**。

> AArch64 `sdiv` 除 0 返回 0，所以如果 `layer[0x24]`/`layer[0x28]` 为 0
> 会让目标矩形退化成 0 —— 这是本轮要验证的假设。
> **实测两者是 1320 / 2232，非零，假设排除。**

## gbuffer 宽度实测 = 1320

把 `not support transform_type` 那条日志的取数源改成 `obj+0x78`
（只改日志，不影响 `cmp w0,5 / cmp w0,0` 的分支），打印结果：

```
OURS:  not support transform_type 1320
```

即 gbuffer 对象宽度 1320，正确。

## 结论

图层结构、gbuffer 尺寸、目标矩形**全部正确**。
差异**不在图层、不在尺寸、不在矩形**。

剩余只有两个可能：

1. **gbuffer 像素内容**是空白/黑屏（宿主画了但画的是空）
2. **paint 画完之后没有真正 present 到窗口**（呈现目标或 ops 调用有问题）

## 下一步（明确做法）

### A. dump 像素内容

paint 里的双缓冲交换（`0x79638c` 起）：

```
x19 = layer+0x20 → gbuffer
     gbuffer+0x30 / gbuffer+0x38 是两块像素指针
ops->fn(0x9117, 0, gbuffer)          ; opcode 0x9117 = 绘制
```

在 `0x7963c4: mov w1, 0` 处把 `w1` 改成从 `gbuffer+0x30` 指向的像素里读一个 dword，
再让 ops 调用前打一条日志（可复用 `not support transform_type` 那条日志的写法）。
两边各取首像素对比即可。

### B. 查呈现目标

`display_present`（`0x796434`）末尾：

```
ops->fn(0x8d40, *(ctx->0x20)->0x20)   ; opcode 0x8d40 = 呈现
```

dump `*(ctx->0x20)->0x20`（最终呈现目标）与 `ctx->0x20`/`ctx->0x28` 的内容，
确认画完是否真的送到了窗口。

## 插桩补丁现状

`sdk/emulator/Emulator` 当前是**字段 dump 版**（4 处基础 + 2 处取数偏移），
另外 `0x79623c/0x796240` 的 `transform_type` 日志取数源被改成 `obj+0x78`。
原版备份 `tmp/Emulator.before_instr`。

字段 dump 的编码方法（docs/50）：

| 偏移 | 编码 | 打印内容 |
|---|---|---|
| `0x79457c` | `0xb9400004 \| (imm<<10)` | `[x0,#imm]` → `num %d`，实际偏移 = imm |
| `0x794584` | `0xb9400000 \| (imm<<10)` | `[x0,#imm]` → `60*值+4`，可反解 |

（`x0` = `buf`，图层起点 = `buf+4`，所以 `imm` = 图层偏移 + 4。）
