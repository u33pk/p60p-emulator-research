# 09 - v2 真机镜像桌面 UI 启动问题：完整调研与修复

日期：2026-10-18
状态：**系统可稳定运行**（不再冻结/重启）。桌面每 ~54 秒自动重启一次（sceneboard IntelligentScene 的 "user unlocked → 重发布失败 → 重启" 自激循环），可用但不完美，见第 8 节。

## 1. 问题现象

v2（6.0.0 模拟器镜像 + 真机 P60P system）开机后：

- 窗口显示开机转圈动画，永远进不了桌面
- 实际上：guest 在开机 ~240 秒时**内核 panic 冻结**，屏幕定格在动画最后一帧（"假转圈"）
- 早前表象：`bootevent.bootanimation.finished=true` 但 `wms.fullscreen.ready=false`、DMS 刷 `GetPrimaryDisplayInfo faild`

## 2. 调研方法

- 对照组：600_test（纯 6.0.0 模拟器镜像，UI 30 秒就绪）
- 全量启动 hilog 采集（`hdc shell hilog > 文件`），抓 v2 / 600_test 启动全窗口对比
- 源码级调研（gitee OpenHarmony-6.0-Release）：ScreenSessionManager::GetPrimaryDisplayInfo、sceneboard 启动链（AMS StartHighestPriorityAbility）、BMS 预装扫描、code signature 校验链
- dmesg avc 拒绝分析、BMS rdb 数据库（guest 自带 sqlite3）取证、host qemu.log/kernel.log 取证
- r2 逆向 patch 系统库

## 3. 根因链（5 层，按发现顺序）

### 根因 1：SELinux 拦截 render_service 访问 express 显示设备【已修】

`dmesg` 证据：
```
avc: denied { read write } comm="RSUniRenderThre" name="teleport_express"
     scontext=u:r:render_service:s0 tcontext=u:object_r:dev_file:s0 tclass=chr_file
```
真机 SELinux 策略没有"render_service 直接打开显示字符设备"的放行规则（真机上 RS 不直接访问 express 设备）。
后果：RS 拿不到 EGL native display（`EGLDisplay is invalid`）→ 无屏幕热插拔 → DMS `screenSessionMap_` 为空 → GetPrimaryDisplayInfo 报错 → sceneboard 启动链（依赖 display 数据）整体卡死。

**修复**：`tmp/rooted_image/p60p_system.img` 的 `/system/etc/selinux/system_common.cil` 追加：
```cil
(allow render_service dev_file (chr_file (read write open getattr ioctl)))
```
debugfs 写回（mode 0644 + ea_set system_etc_file）。开机 libload_policy 编译生效，avc 消失。

### 根因 2：真机指纹导致 BMS 走"重启扫描"流程，共享包安装被跳过【已修】

BMS 开机流程分支（OnBundleBootStart）：
- `USE_PRE_BUNDLE_PROFILE` 且 LoadPreInstallProFile 成功 → 走 install_list/shared_bundles 配置流程（共享包由 `ProcessSystemSharedBundleInstall` 安装）
- 否则 → `ProcessBootBundleInstallFromScan`（只扫 /system/app 一级目录）

v2 中 `GetOldSystemFingerprint()` 非空（指纹来自参数，`emulator 6.0.0.48(...)`，因为 vendor 是模拟器的），走了纯目录扫描：
- `/system/app/shared_bundles/` 下的共享包（Animatronix/CloudCommon/FlexibleLayout/PhotoBrowser/PickerSheet）**从不被处理**
- 一级目录下的共享包目录（如 /system/app/Animatronix）被普通安装器拒绝：`installing cross-app shared library 8519733`（BaseBundleInstaller::CheckAppLabelInfo 拒绝 BundleType::SHARED）
- 失败路径写入 PreInstallExceptionMgr 异常名单，后续开机永久跳过 → **SceneBoard 因依赖 animatronix（SceneBoard_EngineService feature 模块声明依赖）报 8519727 dependency not found，且被异常名单永久跳过**
- 真机不触发是因为出厂 /data 已预装全部 bundle，扫描只处理变更包

**修复**（绕过而非修流程）：
1. patch `libbms.z.so`：唯一带 `b.ne` 跟随的 `cmp w9, #2`（file off 0x35fdd0）改为 `cmp w9, #0x7f5`（SHARED 检查永不命中），普通安装器可装共享包
2. 顺手把 5 个 shared_bundles 路径加进 `/system/etc/app/app_service_fwk_install_list.json`（此路最终因 8521600 "not AppService" 走不通，但无害；不必还原）
3. 清 BMS 数据：`rm -rf /data/service/el1/public/bms/bundle_manager_service /data/service/el1/public/bms/bundle_resources /data/app/el1/bundle/public`（短命令分条执行，长命令 hdc shell 会静默失败）

### 根因 3：本地代码签名 fs-verity 使能失败 -768【已修】

SHARED 检查绕过后，安装推进到 codesign 校验全部失败：
```
CODE_SIGN: [EnforceCodeSignForAppWithPluginId]: Enforcing done, ret = -768
```
`-768 = CS_ERR_ENABLE`：`EnableCodeSignForFile` 里 `ioctl(FS_IOC_ENABLE_VERITY/FS_IOC_ENABLE_CODE_SIGN)` 返回 errno 25 (ENOTTY)——**qemu 内核/文件系统不支持 fs-verity**。真机内核支持故能通过。带 .so 的安装全部死于此；纯 ArkTS 无 so 的包跳过校验才能装成功。

**修复**：patch `libcode_sign_utils.z.so`，3 个导出函数入口（vaddr 0x14618 / 0x146e8 / 0x158e8，file = vaddr - 0x1000）改为 `mov w0,#0; ret`（CS_SUCCESS）。
注：该仓源码实为 `base/security/code_signature`（security_code_signature）。无运行时参数开关（persist.sys.* 无效），编译宏为 CODE_SIGNATURE_ENABLE。

### 根因 6：ucollection 内核驱动 BUG → panic（"永远转圈"的真凶）【已修】

窗口模式能看到动画却在 ~240 秒定格：guest 内核 panic 冻结。kernel.log 证据链：
```
234.1s BUG: sleeping function called from invalid context
       drivers/staging/ucollection/ucollection_process_cpu.c:183
       in_atomic(): 1  Comm: ohos.sceneboard / OS_FFRT_2_3 / hiview...
→ sysrq dump → init StopAllServices → init 写 sysrq 'c' → Kernel panic 冻结
```
`CONFIG_DEBUG_ATOMIC_SLEEP` 在模拟器内核开启（量产机关闭）：`unified_collection_ioctl` 在原子上下文调用 `get_process_load` → 必然 BUG。周期性收集者轮流触发：hiview（~234s 定时）、sceneboard（131s）、RSS。
**修复**：`system_common.cil` 删除所有用户态 `dev_ucollection` allow（hiview/RSS/hap_domain/SP_daemon/gameservice/input_isolate_hap/hidumper 共 8 组规则，保留 neverallowx/init setattr/ueventd/kernel）。加载策略后所有进程 open 被拒 → BUG 不再触发。
（中间尝试过 chmod 000 /dev/ucollection——被 hiview 启动流程重置为 660，不可用。）

### 根因 7：sceneboard "user unlocked" 重启自激循环【未根治】

panic 修复后系统仍周期重启，kernel.log 找到重启原因：
```
reboot.c:121 DoRebootPanic panic caused by reboot.panic:
reboot,panic:SceneBoard exits 4times in 240000ms
```
sceneboard（IntelligentSceneManager）初始化时 `isOsAccountUnlocked=true`（模拟器无锁屏凭证，账号提前解锁）→ `rePublishNtf` 因 `dataShareHelper: undefined` 失败 → "scb restart in user unlocked" → 进程退出重启 → 每代都重查 unlocked=true → 死循环，~54 秒一代。settingsdata 随每次 scb 断开被 AMS "terminate or cache" 杀掉，又加重了 helper 连接不上。
**修复**：`/system/etc/ams_service_config.json` 的 `supportSCBCrashReboot: true → false`（关掉 4 次/240 秒自动重启保护）。系统不再冻结，桌面在每轮重启间隙可用。
**未根治**：重启循环本身（sceneboard 是签名 hap 改不了；需要一个 republish 成功的窗口，鸡生蛋问题）。aab 字符串池证实存在 `private user, no need IntelligentScene` 分支——把用户 100 标记为 private space 用户可整体跳过该逻辑，待调研。

### 根因 4：SELinux 拦截 foundation 访问 devices_security_interface_service【未修，非致命】

```
avc: denied { get } service=devices_security_interface_service scontext=u:r:foundation:s0
```
BMSExt SetRdDevice 失败，只打警告，不阻断安装。暂未处理。

### 根因 5：bm/aa 等 shell 工具在 root 下不可用【绕过，未修】

- `bm`/`aa` 报 `error: failed to execute your command.`：bm 启动时 `OsAccountManager::GetForegroundOsAccountLocalId` 对 uid 0 失败
- patch bm 的 PLT stub（file off 0x3bb90）伪造返回 userId=100/OK 后，bm 仍因 `*.accessToken proxy error 29201`（uid 0 无 access token）失败
- 结论：root 下 shell 工具链不可用，调试手段以 hilog/dmesg/sqlite3/param 为主

## 6. 遗留问题（下一步）

1. **sceneboard/系统应用周期重启**：guest 负载高（真机镜像全量编译），inputmethod/settingsdata 频繁 LIFECYCLE_TIMEOUT，sceneboard 随 watchdog 重启（AMS root-launcher 机制能自动拉起，UI 可恢复）。待查具体超时项，可能需要限制开机并发编译或补资源。
2. **hdc 桥接间歇性掉线**：express-bridge "irq is not enabled" 重复出现，重负载下 hdcd 可能崩。影响调试便利性，不影响系统本身。
3. **boot.completed 未置位**：`bootevent.huksService.ready=false` 等个别投票未投出。UI 不受影响（动画/launcher 已不按它阻塞）。
4. **截屏手段缺失**：`Emulator -instance -screenshot` 走桌面门户静默失败；`snapshot_display` 查不到 displayId。需要其他取证手段（如 RS 帧统计）。
5. **bm/aa root 下不可用**（access token 问题未解）。
6. **SettingsData 崩溃循环**： earlier 在异常名单里装失败过，建议重装或清理其数据（/data/app/el1/100 下对应目录）。

## 7. 关键经验

- BMS 开机安装是"每包双用户两遍"（-u 0 失败单例检查是正常噪声，看 -u 100 的结果）
- BMS 异常名单（PreInstallExceptionMgr）会让失败包被永久跳过；清 BMS 数据是可靠的"重置"手段（但 hdc shell 长命令会静默失败，务必分条+验证）
- 商用版与开源版 BMS 行为有差异（fingerprint 来源、流程分支），开源源码行号仅供定位参考
- r2 patch 时注意 vaddr↔file offset 的段映射（libbms 偏移 -0x1000）
