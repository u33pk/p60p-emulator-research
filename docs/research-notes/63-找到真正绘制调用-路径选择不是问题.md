# 63. 找到真正的绘制调用（0x796154）；路径选择不是问题

日期：2026-10-21

## 二分定位结果

| NOP 的位置 | 6.0.0 屏幕 | 判定 |
|---|---|---|
| `0x796130` + `0x796154` | **34KB 黑** | 绘制点在这两个之一 |
| 仅 `0x796130` | **207KB 桌面** | 该点不是绘制 |
| 仅 `0x796154` | （由上行排除法确定） | **是绘制点** |

⇒ **`0x796154: blr x4` 就是把图画上去的那一步。**

## 两条互斥的绘制路径

```
0x7960e0  bl 0x110c8c4        ; 返回 bool
0x7960ec  b.eq 0x796138       ; false → path B
   ...                        ; true  → 继续算参
0x796130  blr x4              ; path A 绘制
0x796134  b 0x796158          ; 跳过 path B
   ─────────────────────
0x796138  x0 = *(0x7b41920)   ; 另一张 ops 表
0x796140  x4 = [x0]
0x796144  w3 = [x29+0x48]     ; h
0x796148  w2 = [x29+0x44]     ; w
0x79614c  w1 = [x29+0x40]     ; y
0x796150  w0 = [x29+0x4c]     ; x
0x796154  blr x4              ; path B 绘制  fn(x, y, w, h)
```

两条都调 `fn(x, y, w, h)`，但**函数来自不同的 ops 表**（path A 的 x4 在更早处取）。
6.0.0 实测走的是 **path B**（`0x796154`）。

## 实验：在我们这边强制走 path B

把 `0x7960ec` 的 `b.eq 0x796138` 改成 `b 0x796138`（无条件走 path B），
冷启动我们的实例：

```
OURS HOST（强制 path B）  34369 字节  →  仍是黑
```

⇒ **路径选择不是问题。两条路径在我们这边都画不出来。**

## 结论

绘制调用是被正确执行的（否则 6.0.0 不会出屏），
但在我们这边**画出来是黑** —— 说明**绘制的源（gbuffer 纹理）是空/黑**。

这就把问题从"调用链"彻底收敛到"**像素来源**"：
guest 的合成结果没能进入宿主的 gbuffer 纹理。
