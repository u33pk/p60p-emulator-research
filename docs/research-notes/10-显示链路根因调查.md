# 10 - v2 显示链路根因调查：display_composer_service 从未注册

日期：2026-10-18
状态：**根因定位到"devmgr 未将 display_composer 设备派发给 composer_host"这一层；更深一层（为什么）受限于可观测性未闭合**。系统已还原到 12:49 基线（foundation 稳定，不 panic）。

## 1. 用户症状与最终解释

用户带窗口启动 v2，十几分钟卡在开机转圈。本轮证明：

- 转圈 = **guest 侧从未产生过桌面帧**。开机动画播完后 RS 无屏可合成，画面定格/宿主兜底动画
- 真因链：**DMS 无任何 display → 因为 RS 从未上报屏幕热插拔 → 因为 RS 拿不到 display_composer HDI 服务 → 因为 composer_host 从未注册 display_composer_service → 因为驱动 Bind 从未执行 → 因为 devmgr 从未把 display_composer 设备派发给 composer_host**

对照组 600_test（纯模拟器镜像，同 vendor/内核/hcb/sys_prod）一切正常：服务注册、express_hotplug 每秒 open/read、桌面/锁屏截图正常。

## 4. 关键机制记录（r2 逆向结论）

- 驱动 `libdisplay_composer_driver_1.0.z.so`：Bind 里 `IDisplayComposer::Get(true)` → 经 libhdi dlopen `libdisplay_composer_vdi_impl.z.so` → dlsym `CreateComposerVdi` → **ctor 尾部直接调 openfd() 打开 /dev/express_hotplug** 并起 HotplugListening 线程（usleep 1s 轮询）。600 的 kernel.log 就是这个签名。
- 服务注册（HdfServiceObserverPublishService）在 HDF 框架 LaunchNode 内、Bind 之后；**即使 express open 失败服务也照样注册（0 屏静默）**——所以"服务未注册"只能解释为 Bind 没跑完/没跑。
- devmgr 启动循环：`preload!=2 && !(QuickLoad&&preload==1) → hostClnt->AttachDevice`。
- devhost 侧 AddDevice 流程：查重→GetDriver(dlopen)→NodeNewInstance→LaunchNode(Bind→Init→AttachDevice→PublishService)。

## 5. 系统稳定性要点（血的教训）

- **不要 kill render_service**：手机 graphic.cfg 里 `on-restart: reset foundation, reset allocator_host, reset composer_host` → foundation 反复重置 → critical 4 次 → init StopAllServices → sysrq panic（reboot.c:121）。14:42 与 14:52 两次 panic 均源于此（一次我杀的，一次自发）。
- foundation 每 ~50s 干净退出(exit 0)的循环 = 系统级不稳定信号，出现时优先怀疑刚打的镜像补丁（本次即 hcb/ueventd/cil 三补丁引起）。
- devhost "exit 255 → 240s 后重启成功" 是本 franken 组合的常态，排查时需等开机 4 分钟后再看 devhost 状态。
- hilog 字典压缩 + persist 分片里大量记录是 dict 引用，字符串提取只能看到部分记录；"某进程无日志"的结论必须先用"该进程其他日志在不在"校准（本轮用 host-start 记录里有无该 pid 校准）。
