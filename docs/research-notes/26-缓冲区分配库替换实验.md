# 26 — 缓冲区分配卡点：display buffer 库替换实验

日期：2026-10-20

## 目标

继续攻 docs/25 的卡点：`teleport_express can not get fd -1` 导致 `RequestBuffer` 失败，
RS 画不出帧、桌面不出屏。

## 本轮实验与结论

### 1. 定位到手机的海思定制库

手机 render_service 实际加载的是 **`/system/lib64/chipset-sdk/libdisplay_buffer_hdi_impl_v1_3.z.so`**
（海思定制版，64480 字节），以及 `libdisplay_buffer_proxy_1.3.z.so`（47664 字节）。

模拟器自带镜像（`tmp/emu_sys_sub`）里同类库在 **`chipset-sdk-sp/`** 目录，
是**模拟器适配的另一个构建**：

| 库 | 手机镜像 (chipset-sdk) | 模拟器镜像 (chipset-sdk-sp) |
|---|---|---|
| `libdisplay_buffer_hdi_impl_v1_3.z.so` | 64480 (md5 c972114) | 29192 (md5 b9ebb3) |
| `libdisplay_buffer_proxy_1.3.z.so` | 47664 (md5 b3e2b0) | 46760 (md5 03a79e) |

两者的**导出符号完全一致**（`IDisplayBuffer::Get()` for V1_0/V1_1/V1_2/V1_3），
未定义符号也完全一致（各 22 个）——表面上 ABI 兼容。

### 2. 实验 A：两个库都换成模拟器版 → appspawn 段错误

```
Child process appspawn(pid 540) exit with signal : 11
ServiceReap error critical service crashed appspawn → ExecReboot panic
```

guest 整机重启（内核日志里的 "sysrq triggered crash" 是 HarmonyOS 的正常关机流程，
不是内核 bug）。**可复现**，回退后恢复正常。

### 3. 实验 B：只换 `hdi_impl_v1_3`（保留手机的 proxy）→ 安全但无效

- appspawn **不再崩溃**（说明崩溃由 **proxy 库** 引起，impl 换掉是安全的）
- 缓冲区分配**仍然失败**：`Alloc Failed with -1` → `RequestBuffer ret:50002000`
  → `OnDraw failed to request frame`

**结论**：分配失败不在 impl 的逻辑里，在更下游（vendor 的 `ExpressAllocMem` / 宿主通道）。

### 4. 宿主侧证据

qemu.log 里只有每次开机一条：
```
express_gpu_render.c(init_global_gbuffer_data:859) register shutdown_notify_callback.
```
**没有任何 gbuffer 创建错误**（`error when creating gbuffer...` 等都没出现）。
说明失败发生在**请求还没到达宿主 gbuffer 创建逻辑之前**——即 guest 侧取 fd 那一步。

vendor 的 `libdisplay_buffer_vendor.z.so` 中 `ExpressAllocMem` (0x2be8) 的日志：
- 成功路径：`express init gbuffer id %llx ret %d err %d fd %d %d %d pixel %d size %d usage %x`
- 请求路径：`ExpressAllocMem requeset width %d, heigt %d, format %d, usage %lx`
- 失败路径：`teleport_express can not get fd %d error %d!` ← 实测 **fd=-1, error=0**

`error 0` 很可疑：没有 errno 却拿不到 fd，像是协议层"成功返回但没有 fd"
（可能是请求结构体字段错位，或宿主解析出错）。

### 5. 手机 impl 的两段式分配

手机的 impl 里有两条路径（日志串）：
```
AllocMem Passthrough mode failed, use allocator_host
AllocMem error
```
即先走**海思直通分配**（Passthrough，无海思 gralloc 硬件必然失败），
再回退 **allocator_host IPC**（也失败）。这两条日志都是 debug 级，hilog 里看不到。

模拟器版 impl 也有同样的两段式结构，所以换库没改变路径。

## 当前理解

同一个 vendor allocator，600/601 模拟器镜像能正常出帧（`tmp/600_screen.jpeg` 是
真实的 1320x2232 锁屏截图），手机镜像每次都分配失败。差异不在 vendor，
而在**手机 RS 发出的分配请求参数**（format / usage 位）或 **IPC 组包**上。

推测：手机 RS 使用海思私有 gralloc usage 标志位，宿主/express 层解析出错，
返回"成功但 fd=-1"。

## 下一步（按优先级）

1. **抓取分配请求参数**：vendor 的 `ExpressAllocMem` 有请求日志但是 debug 级。
   两条路：
   - 把该日志调用的级别参数改成 error（二进制补丁 vendor 的
     `libdisplay_buffer_vendor.z.so`，注意补 SELinux 上下文）
   - 用 `tmp/ptrace_watch` 在 `ExpressAllocMem` (0x2be8) 下断，dump `AllocInfo`
     的 width/height/format/usage 字段
2. 拿到参数后与 600 镜像的请求对比，定位被拒绝的 usage 位。
3. 若确认是 usage 位问题，在手机 RS/impl 侧屏蔽该位（二进制补丁）。
4. 备选：进一步排查 IPC 组包（`libdisplay_buffer_proxy_1.3` 与 vendor 的
   `libdisplay_buffer_stub_1.3` 之间的结构体对齐）。

## 镜像状态（本轮结束时）

- `librender_service.z.so` —— listener 补丁（0x39b2b8）**保留**
- `librender_service_base.z.so` —— `VK_OHOS_external_memory` **已还原**
- `graphic.para` —— `persist.sys.graphic.GpuApitype=1`
- `chipset-sdk/libdisplay_buffer_hdi_impl_v1_3.z.so`、`libdisplay_buffer_proxy_1.3.z.so`
  —— **已回退为手机原版**（本轮实验全部撤销）
