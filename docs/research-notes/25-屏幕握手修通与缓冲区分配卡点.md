## 一、屏幕握手修复（最关键）

### 机制

`RSMainThread::Init` (librender_service.z.so 0x39a948) 在判 gpuContext 失败后
**直接走函数尾声返回**，跳过了后面的 `RegisterScreenNodeListener` (0x39b914)。

### 最小补丁

把 null 路径上的日志调用换成 `RegisterScreenNodeListener`，注册完仍走原路正常返回：

```
0x39b2b8  bl HiLogPrintDictNew   →   bl RSMainThread::RegisterScreenNodeListener
机器码    0x9405a052             →   0x940006ac
```

**为什么不跳到 0x39b910 继续 Init**：试过（`b 0x39b910`），会跳过 0x39b704~0x39b910 之间
的大量初始化（RSInnovation/RsChipsetVsync/RSBackgroundThread::InitRenderContext/
AccessibilityConfig 等），导致 guest 直接挂死（内核日志停在 20.5s，模拟器心跳丢失）。
**只补注册、其余照旧返回**才是安全做法。

`RegisterScreenNodeListener` 内部自己调 `CreateOrGetScreenManager()`，不依赖被跳过的状态。

### 效果实证

补丁前：
```
NotifyScreenNodeChange: screenNodeListener_ is nullptr!
```
补丁后：该错误消失，且触发一次 composer 重启（`kill $(pidof composer_host)`，
composer 会自动重启并重新热插拔）后：

```
OnHotPlugEvent: screen 0is connected
ProcessScreenConnected The screen for id 0 connected.
ProcessScreenConnected The screen id 0 is set to defaultScreenId.
CreateNodeAndSurface ... name:SCBDesktop5
CreateNodeAndSurface ... name:SCBWallpaper4
CreateNodeAndSurface ... name:BackgroundBlurView
CreateNodeAndSurface ... name:com.ohos.sceneboard
```

## 二、Vulkan 稳定性：字符串补丁要还原

### 问题

设置 `persist.sys.graphic.GpuApitype=1` 后（见 docs/24），模拟器在 guest 启动后 ~20-25 秒
必然死亡（`crash_server.log`: `Client heartbeat lost, exit`），qemu.log 死前必有：

```
Host: Interop extension not available: VK_KHR_external_memory_win32
find null prt!!!
```

对照实验（干净覆盖层、无该参数）：模拟器稳定 300 秒以上。

### 根因

docs/22 里把 `librender_service_base.z.so` rodata 0x22d820 的
`VK_OHOS_external_memory` 改成了 `VK_KHR_external_memory`。
改成标准扩展名后，模拟器宿主侧走 **win32 interop** 通道（`VK_KHR_external_memory_win32`），
而宿主是 Linux 没有这个扩展，转发层卡住 → 心跳丢失 → 自杀。

**还原字符串**（改回 `VK_OHOS_external_memory`）后，Vulkan 路径正常激活
（日志出现 `RSSurfaceOhosVulkan`），模拟器稳定存活。

## 三、当前唯一卡点：缓冲区分配失败

```
allocator_host/DISP: [ExpressAllocMem:251] teleport_express can not get fd -1 error 0!
allocator_host/ALLOC_SRV: AllocMem: AllocMem failed, ec = -1
render_service/allocator_proxy: AllocMem_ failed, error code is -1
render_service/DISP_HDI_BUFF: AllocMemIpc: AllocMem error
render_service/Bufferqueue: Alloc Failed with -1
render_service/Bufferqueue: Fail to alloc or map Buffer[1320 2232]
render_service/Bufferqueue: NativeWindowRequestBuffer: RequestBuffer ret:50002000
RSSurfaceOhosVulkan: RequestBuffer failed 50002000
RSBaseRenderEngine::RequestFrame: request SurfaceFrame failed!
RSScreenRenderNodeDrawable::RequestFrame renderEngine requestFrame is null
RSScreenRenderNodeDrawable::OnDraw failed to request frame
```

分配链路：render_service → allocator_host（`/vendor/bin/hdf_devhost`，vendor 提供）
→ `ExpressAllocMem` (libdisplay_buffer_vendor.z.so 0x2be8) → `/dev/teleport_express` → 宿主。

失败点是**取 fd 返回 -1**（`/dev/teleport_express` 节点存在且 0666，权限不是问题）。

### 与 6.0.0 模拟器镜像的对比（关键）

| 项 | 600/601 镜像 | 当前手机镜像 |
|---|---|---|
| `teleport_express can not get fd` | **2 次** | 每帧都失败 |
| `RequestFrame`/`OnDraw` 失败 | **0 次** | 持续 |
| `RSDrawFrame ... gpuContext is nullptr` | **有**（同样为 null） | 有 |
| 桌面/锁屏 | **正常显示**（600_screen.jpeg） | 不出屏 |

**重要修正**：600 镜像的 render_service **同样有 `gpuContext is nullptr`**，
但桌面照常显示！所以 gpuContext 为空**不是**致命问题，之前的判断要修正。

真正的差异是**缓冲区分配**：同同一个 vendor allocator（p60pv2_vendor.img 就是 601 的
emulator 驱动），601 的 render_service 分配基本成功，手机的 render_service 每次都失败。
差异只可能出在**手机 RS 发出的分配请求参数**（format / usage 标志位，可能是海思私有
usage 位），或分配接口版本（vendor 提供 `libdisplay_buffer_stub_1.0/1.1/1.2/1.3` 四个版本）。

## 四、重要操作教训（本轮踩坑）

1. **改镜像后必须补 SELinux 上下文**：`debugfs` 的 `rm`+`write` 生成的新 inode 没有 xattr，
   会导致库加载失败（render_service `exit with code : 127`）→ critical 服务级联 →
   `ExecReboot panic` 整机重启（看起来像"模拟器崩了"）。写入后必须补：

   ```
   sif <file> mode 0100644
   sif <file> uid 0
   sif <file> gid 0
   ea_set <file> security.selinux "u:object_r:system_lib_file:s0"
   ```

2. **`begetctl stop_service render_service` 会让模拟器整个退出**（critical 服务级联 +
   模拟器心跳看门狗）。要重启 RS 用 `kill $(pidof render_service)`，init 会拉起。

3. **userdata qcow2 损坏会让模拟器段错误**：模拟器异常退出后覆盖层可能损坏，
   表现为启动即 `Segmentation fault`。删掉 `tmp/deployed_p60pv2/HarmonyOS_P60P_v2/*.qcow2`
   重来即可（会丢运行时数据，包括 `param set` 的持久化参数）。

4. **模拟器启动必须用绝对路径**（`-instancePath`/`-imageRoot`），相对路径报 `00801003`。

## 六、下一步

攻缓冲区分配失败：

1. 对比手机 RS 与 601 RS 的分配请求参数（format/usage）。可在 vendor 的
   `ExpressAllocMem` 打日志补丁，或用 ptrace 抓参数。
2. 检查手机 RS 用的是哪个版本的 `IAllocator`/`libdisplay_buffer_stub`。
3. 若确认是海思私有 usage 位，可在 RS 侧屏蔽该位，或在 vendor 侧放宽校验。
4. 另一条路：把 601 的 render_service + 图形库整体换进手机镜像（vendor 本来就是 601 的），
   风险是与手机 foundation/sceneboard 的 RS IPC 兼容性。
