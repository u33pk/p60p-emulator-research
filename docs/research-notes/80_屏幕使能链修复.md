# 80. 屏幕使能链修复：OnHotPlug 注册失败根因 + composer smq fd patch（2026-10-22）

## TL;DR（当前状态）

- **根因已定位并修复（已固化进 vendor 镜像）**：`Init: Failed to register OnHotPlug Func to composer` 的真正来源是
  **composer_host 的 SMQ（共享内存队列）fd 被提前 close**，导致 `IDisplayComposerInterface::Get` 的 IPC
  （`GetCmdRequest`→stub `GetCmdReply_`）在回传 SMQ fd 时 `dup(fd)` 返回 EBADF → stub 返回 -3 →
  RS 侧 `Get` 返回 nullptr → `HdiDevice::GetInstance` 失败 → `RegScreenHotplug` 返回错误 →
  `RSScreenManager::Init` 在 `cbnz w20, 456958` 处打日志并 `return false`。
- **Patch（已验证有效）**：把 `libdisplay_composer_service_1.3.z.so`（vendor）里两处 `close` 打成 NOP，
  SMQ fd 永不被关 → `GetCmdReply` 成功 → 干净启动时 `OnHotPlug(0,1)` 正常、屏幕 0 连接、
  `SetDisplayPowerStatus` 设 ON（vdi return 0）、锁屏能渲染。
- **画面仍不能连续走动（未完全解冻，验收"时钟走动"未达成）**：亮屏状态下锁屏时钟 2 分钟以上字节级不变
  （00:09–00:11 连拍 5 张全同）。剩余 blocker 是 **guest 拿不到持续的硬件 vsync**（详见 docs/77/78/79 + 本文第五节实测）。
- 之前看到的时钟 11:40→11:42→11:44 只是锁屏每次**重渲染/唤醒**取当前时间，不是连续动画（用户 23:50/23:52 复测确认仍冻结）。

## 一、逆向定位：0x1deda 引用点与失败分支

- 目标字符串 `Init: Failed to register OnHotPlug Func to composer.` 在 `_hilog_` 段 **0x1ded4**（vaddr==fileoff）。
  代码通过 **HiLogPrintComm** 引用（tag 在 .rodata、fmt 走 x5/x6 寄存器），不是 HiLogPrintDictNew。
- 引用点：`RSScreenManager::Init`（`_ZN4OHOS5Rosen4impl15RSScreenManager4InitEv`@**0x456678**）：
  - `0x456960: adrp x5,1d000; 0x456964: add x5,x5,#0xed4` → x5=0x1ded4（本字符串）
  - 该分支由 `0x456794: cbnz w20, 456958` 进入：w20 = `HdiBackend::RegScreenHotplug(cb,this)` 的返回值，**非 0 即失败**。
  - 失败路径：打完日志后 `0x456990: mov w0,wzr` → **Init 返回 false**。
- Init 里其余注册失败都**只打日志继续**：`RegScreenRefresh`(0x1de99)→继续；`RegHwcDeadListener`(0x1df4f)→返回 false；
  `RegScreenVBlankIdleCallback`→继续。**只有 RegScreenHotplug 失败会中止 Init**。
- 调用链：`Init` → `HdiBackend::RegScreenHotplug`（libcomposer 0x124c0）→ `HdiDeviceImpl::RegHotPlugCallback`（0x18438）
  → `IDisplayComposerInterfaceV1_3::RegDisplayHotPlugCallback`（composerSptr 虚函数 +0x20）→ IPC → composer_host。

## 二、失败根因：composer_host SMQ fd 被提前 close（GetCmdReply -3）

干净启动（及运行一段时间后）render_service 启动日志确凿链：
```
RSHardwareThread: Start()!
composer_host/MessageParcel: WriteFileDescriptor 246: dup failed, fd:9, errno:9   ← EBADF
composer_host/smq: Marshalling: failed to write ashmemFd_
composer_host/display_composer_stub: DisplayComposerStubGetCmdReply_: write reply failed!
render_service/display_composer_proxy: GetCmdReply_ failed, error code is -3
render_service/DISP_CMD: Init: GetCmdReply failure, ret=-3
render_service/DISP_CMD: DisplayCmdRequester init failed
render_service/DISP_HDI_COMP: Create: Create DisplayCmdRequester failed 54
render_service/Composer: Init: IDisplayComposerInterface::Get return nullptr.
render_service/Composer: GetInstance: hdi device get instances failed.
render_service/Composer: InitDevice: Get HdiDevice failed
render_service/RSScreenManager: Init: Failed to register OnHotPlug Func to composer.
render_service/RSHardwareThread: RSHardwareThread CreateOrGetScreenManager or init fail.
```
- fd 9 是 SMQ（SharedMemQueue）的 ashmem fd。`/proc/<composer>/maps` 里可见多个
  `/dev/ashmem/hdi_smq (deleted)`（fd 已关、映射还在），也有仍打开的 `/dev/ashmem` fd。
- 机制：composer_host 的 `DisplayComposerService` 在 SMQ 重建/析构时把旧 fd `close` 掉，
  但 `GetCmdReply` 仍把带已关闭 fd 的 SMQ 对象回传给客户端 → `dup` EBADF。
  （不依赖 RS 重启次数，**干净启动首帧即触发**。）

## 三、Patch：NOP 两处 close（已固化 vendor 镜像）

文件：`/vendor/lib64/libdisplay_composer_service_1.3.z.so`（部署版 md5 fde06192468832b4d9ad49dcef745986）。
该库 `.text` vaddr = fileoff + **0x1000**。

| vaddr | 指令 | 含义 | patch |
|---|---|---|---|
| 0x1fc58 | `bl 206a0 <close@plt>` (0x94000292) | SMQ 创建时 close 旧 fd | → NOP 0xd503201f |
| 0x1fef8 | `bl 206a0 <close@plt>` (0x940001ea) | SMQ 包装类析构 close fd(+24) | → NOP 0xd503201f |

效果：fd 泄漏但永不被关 → 客户端 dup 永远成功。fd 消耗极小（每次 RS 生命周期几个），可接受。

**patch 后 md5**：2a230836fa7746d4238698e7e2088119（已写回 `tmp/rooted_image/p60pv2_vendor.img`，
debugfs rm/write/sif mode 0644/ea_set security.selinux=u:object_r:system_lib_file:s0，qcow2 已删）。

## 四、验证结果（干净启动，2026-10-22 23:39 重启）

- `hilog -x | grep -c 'Failed to register OnHotPlug'` → **0**
- `hilog -x | grep -c IsAllScreensPowerOff` → **0**（干净启动下也不再报）
- `hilog -x | grep -c 'no vsync'` → 0（boot 初期）
- 启动日志：`OnHotPlug(0,1)` → `ProcessScreenConnected` → `PhysicalScreenInit: RSScreen(id 0) start SetScreenPowerStatus to On`
  → composer `SetDisplayPowerStatus ... vdi return 0` → `end SetScreenPowerStatus to On` → `Init succeed`。
- 锁屏能渲染（时间/日期/未成年模式横幅可见），uinput 滑动能解锁进桌面。
- **但**：2 分钟截图 cmp 仍相同（时钟非连续走动）。之前看到的 11:40→11:42→11:44 只是锁屏每次**重渲染**取当前时间，不是连续动画。

## 五、剩余 blocker：硬件 vsync 未流入 guest（实测确认，本修复未触及）

干净启动 + OnHotPlug 修复后实测（00:0x，非侵入 /proc 采样）：
- **RS 主线程冻结**：`render_service` 主线程 utime/stime 8 秒不增（无 vsync 驱动渲染）。
- **宿主 paint 通道正常**：`Log/qemu.log` 里 `opengl_paint_composer_layers` 一直被调用（44475 次，多为历史
  10-20 的 `gbuffer_from_global_map is null` 噪声）；灭屏时 `display terminate` 是正常行为。
  即"宿主 paint 断流"（doc 77 旧状态）已不成立——现在是 **guest 根本不送新帧**。
- **composer_host 空闲**：持 `/dev/express_sync`×4、`/dev/express_display`、`/dev/teleport_express`×3，
  线程全部 futex/binder 等待，vsync 不来。
- **两条 vsync 源都不通**：
  1. composer `RegRefreshCallback`/`RegDisplayVBlankIdleCallback` 在**部署版和 EMU 版 vdi_impl 里都是硬编码返回 -2 的桩**
     （显示 vsync 不走 composer 回调，官方模拟器也一样）。
  2. `chipset_vsync` 是**被动通道**（docs/79 已逆向：SetCallback/GetVsyncInfo/VoteFrameRate，服务拉取+电源投票，不推 vsync）。
- **VSyncGenerator 卡硬件模式**：docs/79 实测 generator 对象 +281 字节 mode=1（hardware），开机时硬件 vsync 曾短暂
  流通并校准 period=15622783ns(64Hz)，随后断流 → 发生器在硬件模式空等。`VSyncSampler::UpdateModeLocked`
  （libvsync @0x46770）负责按采样计数（+420）裁决模式，硬件 vsync 停后未正确回退软模式。

**结论**：时钟要自发走动，必须让 generator 持续收到 vsync 或回退到自跑软模式。这是 guest 侧无独立硬件
vsync 源 + sampler 不回退共同造成的，**不是 guest 镜像里改几个字节能修的**（docs/77-79 三篇亦未解决）。

## 六、下一步候选（按时序/性价比排序）

1. **强制软 vsync（guest 侧，最直接）**：让 `VSyncSampler::UpdateModeLocked`（libvsync @0x46770）在硬件 vsync
   停采后回退软模式，或运行时把 generator+281 的 mode 写 0。风险：改错会崩 RS，需先在运行进程上 lldb 验证
   （注意 doc 79 备忘：attach 后 detach 会致 RS 重启；本轮多次 lldb handshake 失败疑似把 RS 搞挂，优先用
   /proc/<pid>/mem 直读免停采样）。
2. **补真正的 vsync 源**：宿主 express_display 是否会给 guest 推 vsync（查 `express_sync` fd 是否有周期数据、
   宿主 express_display.c 的 vsync 产生逻辑）；若宿主本来就不推，则与 doc 77 一致属宿主侧问题。
3. **查 SetScreenVsyncEnabled 使能链**：断 `RSScreen::SetScreenVsyncEnabled`（librender_service @0x19aa04，
   经 vtable）→`HdiScreen::SetScreenVsyncEnabled` 的调用方（0x41338 内嵌回调 lambda），确认屏幕已连接+上电后
   为何 hardware thread 不使能（可能同样因无 vsync 而空转）。
4. guest 时钟跳变（doc 79 提到 30s 走 12 分钟）独立问题，会扭曲所有计时判据，建议单独立案。
