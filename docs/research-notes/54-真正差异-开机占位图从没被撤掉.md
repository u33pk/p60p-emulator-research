# 54. 真正的差异：开机占位图从没被撤掉（与 paint/present 无关）

日期：2026-10-21

## 三个关键对照（同一宿主二进制）

| 配置 | 窗口屏幕区 | 判定 |
|---|---|---|
| 6.0.0，正常 | **206KB** 桌面 | 出屏 ✓ |
| 6.0.0，**禁用 display_present** | **34KB 黑屏** | 占位图**已被撤掉** |
| 6.0.0，**禁用 paint + present** | **34KB 黑屏** | 占位图**仍被撤掉** |
| 我们，正常 | 42KB 占位图 | 占位图仍在 |
| 我们，**禁用 display_present** | **42KB 占位图** | **占位图从没被撤掉** |

## 结论

**问题不是"guest 帧没被呈现"，而是"模拟器的开机占位图从没被撤掉"。**

而且这个"撤掉"动作：

- 在 6.0.0 上**与 paint、present 都无关**（两个都禁用照样撤掉）
- 在我们这边**从不发生**

⇒ 差异在**比 paint/present 更早的流程**里。

另外确认：`display_present` 的 ops 调用（`0x79653c: blr x2`）确实是把 guest 帧放到屏幕上的机制
（禁用后 6.0.0 从桌面变成黑屏）。但它不是占位图的撤除者。

## 占位图是什么

窗口屏幕区是「黑底 + HarmonyOS logo + 转圈」，**转圈是动画**（4 秒内 738 字节变化）。
它不是静态图片，而是模拟器 UI 在持续绘制的"开机中"画面。
`sdk/emulator/` 目录下没有对应图片资源，`Emulator` 二进制里 `HarmonyOS` 字符串也只有
CLI/协议文案 —— 说明它可能是内嵌资源或程序绘制。

## 下一步（明确方向）

查**什么撤掉占位图**。已知它与 paint/present 无关，所以候选只剩显示握手早期的几个事件：

1. `display_context_init`（`display_decode_invoke:504`）
2. `MAIN_CREATE_CHILD_WINDOW`（`display_context_init:509`）
3. `FUNID_Get_Display_Mods` / `Get Display` / `device type` 这几步握手
4. guest 侧某个"就绪"信号（funId 10 `ShowWindow` 会置 `ctx->field_0x60=1`）

做法建议：
- 在 6.0.0 上把 `display_context_init` / `MAIN_CREATE_CHILD_WINDOW` 逐个 NOP，
  看哪个会让占位图**不被撤掉** —— 反向定位出撤除者
- 或在宿主里找占位图的绘制点（搜内嵌资源 / QPainter 绘制 / QTimer 动画）
