# 62. 绘制调用点排查：0x7963cc 不是画桌面的那一步

日期：2026-10-21

## 实验

NOP 掉 `opengl_paint_composer_layers` 里 `0x7963cc: blr x2`
（opcode `0x9117`，`ops->fn(0x9117, 0, gbuffer)`），
在 6.0.0 上冷启动看屏幕变化。

## 结果

```
600 HOST（绘制已禁用） 206943 字节  →  桌面照常显示
```

**桌面仍在** ⇒ 这个调用**不是**画桌面的那一步。
（对比：禁用 `display_present` 会变黑 34KB，说明 present 是必需的；
禁用 paint+present 也变黑。但 paint 里这个具体调用不是关键。）

## paint 函数的间接调用全图

`opengl_paint_composer_layers`（`0x795df4` – `0x7966a4`）内共 9 处 `blr`：

| vaddr | 位置 | 说明 |
|---|---|---|
| `0x795f20` | 循环前 | — |
| `0x796130` | 循环体内（目标矩形区） | ← 候选绘制点 |
| `0x796154` | 循环体内 | ← 候选绘制点 |
| `0x796184` | 循环体内 | ← 候选绘制点 |
| `0x7961d8` | 循环体末 | ← 候选绘制点 |
| `0x796298` | gbuffer 查找 | `f(layer+0x14, layer+0x18)` |
| `0x7963cc` | 循环后 | **本轮证伪**：不是绘制 |
| `0x7963fc` | 循环后 | — |
| `0x79640c` | 循环后 | — |

（`0x79653c` 属于 `display_present`，是呈现，已确认必需。）

⇒ 真正的绘制大概率在**循环体内那 4 个**（`0x796130/0x796154/0x796184/0x7961d8`）。

## 结论

绘制路径比预想的复杂，`0x7963cc` 那条（`ops->fn(0x9117,...)`）
是循环后的收尾动作，删掉不影响出屏。

## 下一步

1. **逐个 NOP 循环体内的 4 个 `blr`**，在 6.0.0 上找出真正画桌面的那个
   （4 次冷启动，或一次 NOP 两个做二分）
2. 找到后，在**我们的镜像**上做同样 NOP，看是否本就画的是黑
   （如果 NOP 前后都是黑 → 那个调用在我们这边就没生效）
3. 或直接看那 4 个 `blr` 的目标函数（`ldr xN, [表]` 后 `blr xN`），
   反查它们是什么接口
