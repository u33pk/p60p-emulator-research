# 12 - 信号陷阱二分法：整条链路钉到 devmgr 查询的最后一环

日期：2026-10-18（晚场）
方法突破：**drv10/libhdf_host 的日志全被 hilog 字典压缩（chunks 和实时查询都不可见），改用"信号陷阱"做无损二分**——把指定日志调用点改成 udf(SIGILL 4)/brk(SIGTRAP 5)/BL abort(SIGABRT 6)，kernel.log 的 `exit with signal : N` 精确指出执行到的最后一个位置。镜像已全部还原基线（验证系统稳定）。

## 1. 二分结果（每步一次启动，kernel.log 读数）

| 陷阱位置 | 信号 | composer_host | 结论 |
|---------|------|---------------|------|
| drv10 Bind 入口（enter 日志点） | 4 | **死** | Bind 确实执行（此前"无日志"是假象） |
| drv10 create-host 失败路径 | 6 | 没死 | HdfDisplayComposerHost 创建成功 |
| drv10 Get(true) 失败路径 | 5 | 没死 | IDisplayComposer::Get 成功（VDI/stub 拿到） |
| drv10 Init 入口 | 4 | **死** | Bind 全链通过，Init 执行 |
| libhdf_host LaunchNode publish 调用后（共享库，全部 host 都中陷阱） | 4 | **死(×8)** | **publish 调用已发出且返回** |
| libhdf_host publish 失败分支 | 5 | 没死 | **publish 返回成功！** |
| libhdf_host attach 调用后 | 4 | **死** | publish 成功后 attach 也已调用 |

**结论：host 侧整条链路 100% 健康**（预载→AddDevice→node 创建→Bind→Init→PublishService 成功→AttachDevice）。失败点缩到：**publish 已交付 devmgr 且返回 OK，但服务查询永久 not-found**。

## 2. devmgr 内存取证（新工具 ptrace_grep：进程内存全文检索）

对 devmgr(130) 搜 `display_composer_service`，30 处命中：
- `u:object_r:hdf_display_composer_service:s0` —— SELinux 服务标签（cil）
- 3× `t found<name>` —— 运行时拼装的 "not found" 日志（证明查询确实落空）
- `serviceName..display_composer_service..preload....permission...` —— hcb 解析出的设备信息结构（正常）
- **关键**：`...display_composer_service........display_composer_service........light_interface_service...`（0x7f9c25bf60）——**服务名在 devmgr 的定长 char[32] 名字表里**（与 user_auth 的条目同表同布局：user_auth 27 字符+5 点填充=32，composer 24+8=32，数学自洽）
- `Of[...kkdisplay_composer_service....libdisplay_composer_driver_1.0.z.so.device0` —— 含驱动模块名的记录

对照 user_auth_interface_service（11 处命中，含同一张名字表、live 记录、SELinux 标签）。

## 3. 当前根因表述（最精确）

```
host 侧:   全链健康，publish("display_composer_service") → devmgr 返回 OK
devmgr 侧: 服务名进了名字表（char[32] 数组），记录存在
查询侧:   StubGetService("display_composer_service") → not found（运行时日志实证）
```

**矛盾点**：记录在表但查找落空。嫌疑集中在 devmgr 查询路径对该条目的判定：
1. 条目的状态/有效标志位为 0（publish 只写了名字，记录字段未激活？）
2. 查询走另一张表（live record hash/list vs 静态名字表——我看到的可能是静态表）
3. 服务被标记为 private/仅宿主可见（policy 字段）
4. 名字表条目与 live 记录未链接

## 4. 工具资产（本场新增）

- `tmp/ptrace_bt.c` → ptrace_bt：guest 内线程栈回溯（FP 链，±2 帧可靠）
- `tmp/ptrace_grep.c` → ptrace_grep：进程内存模式检索带上下文（±96B），取证神器
- 信号陷阱方法论：日志不可信时，用信号号当一比特探针；同库共享时观察全部 host 的集体死亡分布也是信息
- 编译命令：`clang --target=aarch64-linux-ohos -O2 -static`

## 5. 下一步（按序）

1. **devmgr 查询路径静态分析**：r2 反编译 StubGetService/查询循环，弄清查找用的表结构，对照第 2 节的内存布局确认 composer 条目缺什么字段（状态位？service 指针？）。
2. **live 记录头对比**：ptrace 精确 dump user_auth 与 composer 两个 live 记录的前 64 字节（名字表条目基址 ±0 偏移），diff 出标志位差异。
3. 若确认是标志位/链接缺失 → 反向补丁 host 侧 publish 参数（policy/deviceObject）或 devmgr 侧接受逻辑。
4. 若查询路径无解 → 运行时强制重注册：借 devmgr 的动态加载入口（hdf_kevent 注入 add 命令）绕过启动期注册。

## 6. 纪律与坑位记录

- ptrace_bt 的 FP 链超过 2 帧不可靠（遇 data 区即断）；信号陷阱不受此限
- 双实例并行 = 宿主内存耗尽（HostFreeMemMonitor 0GB）→ qemu 静默死亡，kernel.log 无 panic 假象。任何时候只跑一个实例
- 共享库陷阱会崩掉全部 host（本场用此特性做了集体行为观测，事后必须立即还原）
- kill composer_host 安全（devmgr <13s 重生）；kill render_service 永远禁止
