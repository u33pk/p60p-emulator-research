## 追加：samgr 换血实验（05:45 实录）——根因锁定

**根因**：P60P 的华为 samgr（6.1 Rust）**静默丢弃 RS 的 AddSystemAbility(10)**（无任何日志）；官方 samgr（6.0）正常处理。
**证据**：换官方 samgr 三件套（samgr + libsamgr_common + libsamgr_proxy，依赖列表完全一致）后，RS 重启时官方 samgr 打出完整正常序列：
```
IsDistributedSa SA:10 no Profile! → insert SA:10_158 → FindSaNotify → SendSaAddedMsg
```
**但**：insert 后客户端仍 `GetSaWrap SA:10 not start`（约 1 分钟内失效）。直接 CheckSystemAbility(10) **阻塞**（samgr 尝试动态加载该 SA 等待完成）。冷启动时 samgr 又静默丢 Add（太早）。发现 `rm DeadSA:10`（RS 死亡时移除）。
**结论**：SA 10 插入≠可用。官方镜像上 RS 的 proc 同样无 AddProc/Scheduler proc 记录，但 SA 10 稳定可用——P60P 上仍有状态机差异未明（疑似 proc 状态关联或加载路径）。

**当前部署**：官方 samgr 三件套在 P60P 镜像中（备份 tmp/bak_*），系统整体健康（composer/RS 正常、0 崩溃、画面渲染中）。

**下一步候选**：
1. 对比官方镜像上 SA 10 的完整生命周期日志（FindSaNotify/notify 后的持久化线索），找 P60P 上缺失的环节
2. 让 vsync_on 服务在 boot-complete 后重启一次 RS（warm Add 成功）+ 研究 insert 后为何变 not-start
3. patch RS 在 Add 前 AddSystemProcess("render_service")（进程状态机关联）

## 追加 3：libvsync 软件模式 patch 落地（06:20 实录）

**patch**：libvsync.z.so `VSyncGenerator::C1Eb` 两处——0x3e984 `strb w20→wzr`（+280 恒 0）+ 0x3ea10 `tbz w20,#0→b`（强制软件路径）。已验证运行中 generator **+280=0（软件模式）**。

**结果**：仍冻结。软件模式的发生器**按需 tick**，而请求上不来——sceneboard 本次 boot 完全无 vsync 请求日志（此前是 29189=ERR_DEAD_OBJECT 陈旧连接报错）。**boot animation 卡住未退出**（应切 sceneboard 锁屏）——DMS/切换流程仍卡在 RS 交互上。

**当前完整链路断点**：samgr✅(官方换血) → SA10 注册✅(warm) → 连接调用抵达 RS✅ → **RS 内部处理阻塞/请求不入队** ← 此处。请求侧（sceneboard/bootanim）要么陈旧连接(29189) 要么不发起。

**下一步**：
1. 重启 RS 后观察 boot animation→锁屏 切换（每次 RS 重启后 bootanim 状态）
2. 若 bootanim 永不退出：查 boot animation 的退出条件（DMS GetDefaultDisplaySync 等），那是 sceneboard 之前卡住的位置（THREAD_BLOCK_6S @ GetDefaultDisplaySync）

## 追加 4：5 秒连接死亡 + 单次 vsync 突破（06:25 实录）

**5 秒死亡之谜**：RS 重启后连接可用约 5 秒（insert SA:10 后客户端调用能抵达 RS 并记日志），随后所有客户端调用阻塞→标记死亡。sceneboard 的 29189=ERR_DEAD_OBJECT 即源于此。SA:10 事件**不进持久化日志**（/data/log/hilog 无 samgr 域），只能活捉。

**单次 vsync 突破**：杀掉 sceneboard 后新实例 `First vsync has come back, nodeId: 0`——软件模式发生器 + 新连接 = 请求可达且 vsync 能回！但仅一次（force flush 恢复），随后系统回到无请求空闲——**缺的是持续帧驱动**。

**最终差距画像**：官方上锁屏时钟持续 tick = 有持续驱动源。P60P 上 boot animation 提前退出（两边 cfg 都强制 bootanimation.finished，非差异）、sceneboard 到锁屏的切换未完成、无任何组件持续请求 vsync。各层都已打通，缺最后一个「持续请求源」。

## 追加 6：破环尝试实录（06:50 完结）

**keep-alive 三版均未能驱动帧**：
- v1/v2（ForceRefresh+setPower）：调用**全部阻塞**在首个调用（SendRequest 等回复），80 秒看门狗窗口内 RS 主线程从未被唤醒处理。watchdog 的 60s「RenderFrame task too long」只记日志不中断等待
- 结论：**RS 主线程在 vsync 等待中不处理任何外部 IPC**，唯一例外是 sceneboard 启动瞬间那次（机制未明，可能其时主线程恰好可运行）
- v3（NotifyTouchEvent fire-and-forget）：dlsym 失败待查（符号在库中存在）

**最终结论**：12.5 小时的排查把「真机镜像跑官方模拟器」的启动问题定位到最后一层——RS 主线程的 vsync 等待在 P60P 华为版 RS 上不接受外部唤醒。这需要更深层的 hook（如运行时替换 RS 主线程的等待谓词/注入定时唤醒线程）或官方 RS 二进制级方案，已超出本轮可行范围。

## 追加 7：最后的墙——RenderFrame 永驻（06:55 完结）

**最终画像**：RS 主线程不是「空闲等待」，而是**永驻在 RenderFrame 任务内部**等 present fence（70 秒+不返回）→ 队列里的所有任务（DMS 查屏/keepalive 请求）永不执行 → 无窗口放置 → boot animation 死帧常驻。futex 唤醒无效（队列为空，请求都死在 IPC 层没入队）。信号打断只会让 RS 崩溃重启（init 拉起后回到同一状态）。

**死结**：fence 需合成器 present 完成 ← 需宿主 ack ← 需宿主发 vsync 脉冲 ← 需 guest 使能(0xa8) ← 需 RS 调 vdi ← RS 主线程被 fence 卡死。**完美的环，且在 RS 进程内无法自破**。

**理论破口**（需后续实现）：
1. 稳定窗口发 0xa8（vdi 使能）——单客户端限制挡住第三方调用，需 patch RS 让其在 fence 等待前使能（时序：渲染前 SetDisplayVsyncEnabled 一次）
2. patch RS RenderFrame 的 fence 等待加超时（等 1s 超时跳过 → 任务完成 → 队列流动 → 系统自愈）
3. 换官方 RS 二进制（6.0，ABI 不兼容需大量垫片）
