# 17 - 双重修复落地：composer 服务可查询 + VDI 激活，剩最后一公里

日期：2026-10-18（收官场）
**根因（双重）找到并修复**：
1. **devmgr 单例错位**：get 处理器（0xb244）经 `DevmgrServiceGetInstance` 读全局槽 [adrp14000+0x748]，该槽为 0 时走 lazy 路径拿到**错误对象**（+0x68 是代码指针的 DevmgrService），GetObject 遍历野"表" → 一切查询 not-found。add 走 `DevSvcManagerGetInstance`（另一槽）→ 成功。**修复：0xb26c `bl DevmgrServiceGetInstance` → `bl DevSvcManagerGetInstance`（4 字节补丁）**
2. **SELinux 缺规则**：composer_host 域无 dev_file chr_file 放行（手机 cil 只给了 hisi 设备类型），VDI openfd(/dev/express_hotplug/display) 被拒 → 热插拔永不启动。**修复：cil 加 `(allow composer_host dev_file (chr_file (read write open getattr ioctl)))`**

## 追加：最后 1 英寸精确定位——func 0xb 注册/心跳缺失

- RS 侧陷阱（libcomposer InitDevice 失败分支→udf）：**零触发** → RS 的 HdiDevice 创建成功，SMQ 通道建立
- 内核 ioctl 序列对比（决定性）：
  - 600（正常）：`a0000000b`(func 0xb)×7 → `a01000010/0c/0e/11/0a`(显示序列) → 显示出现；func 0xb 周期性重复（95 次/会话，≈心跳）
  - v2（病）：**func 0xb 零次** → 直接 a01 显示序列（仅 5 条，16.5s 爆发后再无）→ ioctl 挂死（host 不应答未注册客户端）
- 结论：模拟器 composer VDI 的 express 通道**注册/握手步骤（func 0xb）在 v2 被跳过或失败**，后续显示 ioctl 悬挂，VDI 初始化永不完成，GetScreenNum 无返回，无 "screen num" 日志
- 下一动作：r2 追 vendor_composer 的 ExpressConnection::Init 序列，找 func 0xb 的发送条件（哪个检查使 v2 跳过）；或对比 600 运行时该函数的行为差异

## 追加：最后 1 英寸的精确定位与本轮结论

**func 0xb 方向修正**：0xb/0xd 是 GPU teleport 心跳（600=emulator RS 95 次，v2=phone RS 0 次）——与显示无关。显示命令序列（a01 系列）两边相同，宿主 qemu.log 实证 **host 收到了显示查询并应答（"Get Display id: 0, power state:0"）**，且 1320x2232 显示模式数据已在 composer 内存中——**VDI 枚举实际成功**。

**三角定位（三个信号陷阱全零触发）**：
- VDI GetDisplayCapability 入口陷阱：零触发
- svc13 ProcessRequestCmd（SMQ 命令分发）陷阱：**零触发**
- libcomposer InitDevice 失败分支：零触发（设备创建成功）
→ **RS 创建了 composer 设备（SMQ 初始化发生，ashmem×2 实证），但之后从未发送任何显示命令**。persist.rosen.hardwarecomposer.enabled=1 实验排除该参数门。
→ 阻断点精确定义：**手机版 RS（6.0.0.107）在 InitDevice 成功后的显示查询步骤未执行**（对比 600 同位置会立即 GetDisplayCapability）。候选：RSScreenManager 后置流程的某个分支条件（版本协商/devicetype/能力检查）静默跳过。

**遗留工具清理**：VDI/svc13/libcomposer 三个诊断陷阱已还原，镜像 = 生产修复状态（devmgr 单例补丁 + composer_host SELinux + RS 时序 + doc09 全套）。已验证开机稳定。
